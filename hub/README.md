# Chest Memory — постоянный клан-хаб

> ## ⚠️ БЕЗОПАСНОСТЬ: `config.php` больше не хранится в git
>
> Ранее файл `public/config.php` был закоммичен вместе с рабочим токеном.
> Токен из истории репозитория следует считать **скомпрометированным навсегда**.
>
> **Что сделать на сервере:**
>
> 1. Сгенерировать новый токен: `openssl rand -hex 12`
> 2. Записать его в `.clan_token` и в `public/config.php` (файл теперь в `.gitignore`)
> 3. Раздать новый токен участникам клана — старый перестанет работать
> 4. Переписать историю git (`git filter-repo --path hub/public/config.php --invert-paths`),
>    иначе старый токен остаётся доступен в любом клоне репозитория
>
> Токен — единственная аутентификация хаба: любой, кто его знает, может читать все
> сессии, подменять участников и удалять чужие сессии. Не коммить его снова.

## Аутентификация игроков (новое)

Раньше хаб доверял полю `uuid` из тела запроса — любой участник мог выдать себя за
другого: снять чужой claim, «принести» материалы за него, закрыть сессию. Теперь есть
проверка через Mojang, та же, что при входе на обычный сервер:

```
GET  /v1/auth/challenge          -> {"nonce": "..."}
     мод вызывает Mojang joinServer с этим nonce
POST /v1/auth/verify {name, nonce} -> {"token", "uuid", "name"}
     дальше все запросы с заголовком X-Clan-Session: <token>
```

Access token игрока **не покидает клиент** — его видит только Mojang. Хаб лишь
спрашивает у Mojang «этот игрок правда тот, за кого себя выдаёт».

**Как включить (два шага, чтобы никого не выкинуть):**

1. Обновите хаб и мод. Пока `REQUIRE_AUTH` выключен, работают и старые клиенты.
2. Когда все обновились — включите строгий режим:

   Python: `REQUIRE_AUTH=1 python3 clan_hub.py`
   PHP: в `config.php` добавьте `'require_auth' => true,`

После включения запрос без проверенной сессии получает `401 auth required`.

Общий токен (`CLAN_TOKEN`) остаётся, но теперь это **приглашение**, а не удостоверение
личности: даже если он утечёт, действовать от имени конкретного игрока уже нельзя.

## Что сохраняется

- Все сессии (`CM-XXXX`), claim’ы, progress, staging keys  
- Файл: `data/sessions.json` (атомарная запись после каждого изменения)  
- После **ребута VDS / падения процесса** данные **не пропадают** (нужно снова запустить watchdog)

## Вариант A — Python + watchdog (сейчас на VDS)

```bash
cd ~/chestmemory-hub   # или /var/www/h001628/data/chestmemory-hub
bash start.sh
cat .clan_token
cat lt.url             # временный URL (loca.lt) — может смениться
```

Watchdog каждые 20 с поднимает хаб (и туннель), если упал.

**После ребута сервера** один раз зайди по SSH и снова `bash start.sh`  
(или добавь эту команду в **Cron панели ISPmanager** → `@reboot`).

В моде:

- URL: из `lt.url` (или постоянный — вариант B)
- Токен: из `.clan_token`

## Вариант B — постоянный HTTPS (рекомендуется)

Без localtunnel, URL не прыгает:

1. В панели ISPmanager: **WWW → создать сайт** (бесплатный DuckDNS или свой домен).  
2. Document root → папка `chestmemory-hub/public`  
3. Скопировать `public/config.sample.php` → `public/config.php`, прописать тот же token.  
4. SSL (Let’s Encrypt) в панели.  
5. В моде URL: `https://твой-домен` (без порта), токен из config.

PHP пишет в тот же `data/sessions.json`.

## Файлы
